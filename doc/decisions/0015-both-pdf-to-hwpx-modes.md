# 결정 0015 — PDF → HWPX 는 두 방식을 모두 준다

- 날짜: 2026-09-15
- 상태: **적용됨**
- 정한 것: [문서 변환기 화면](../../converters/web/src/panel.ts)이 "둘 중 무엇을 만들지
  정하지 않았습니다" 라고 적어 두었던 자리
- 관련 계획: [변환 구현 계획 1·3단계](../../converters/IMPLEMENTATION_PLAN.md)

## 결론

쪽을 **그림으로 심는 방식**과 글자를 **다시 짜 맞추는 방식**을 둘 다 만들고,
어느 쪽을 쓸지는 저장 단추에서 사람이 고른다. 하나를 골라 다른 하나를 버리지 않는다.

```text
PDF 편집기의 쪽 목록 ─┬─ [HWPX 이미지로 저장] → 보이는 대로, 편집 불가
                      └─ [HWPX 텍스트로 저장] → 편집 가능, 배치는 추정
```

## 왜

둘은 같은 기능의 두 구현이 아니라 **서로 다른 것을 지키는 두 기능**이다.

| | 이미지 | 텍스트 |
|---|---|---|
| 지키는 것 | 보이는 모양·쪽 순서 | 고칠 수 있는 문단·표 |
| 못 지키는 것 | 글자 편집·검색·용량 | 그림·수식·원본 배치 |
| 실패하는 입력 | 없음 (그림은 언제나 나온다) | 스캔 PDF (글자가 없다) |
| 크기 | 200DPI 3쪽 87KB | 같은 3쪽 29KB |

규격서에서 표 한 줄을 고쳐야 하는 사람에게 그림은 쓸모가 없고, 결재 문서를
그대로 붙여야 하는 사람에게 추정된 배치는 위험하다. 한쪽만 만들면 나머지 절반은
이 도구를 못 쓴다.

두 벌을 들여도 갈라지는 코드는 없다. HWPX 패키지 생성부(`hwpx-writer.ts`)가
한 벌이고, 두 방식은 그 안에 넣을 쪽을 그림으로 만들지 글로 만들지만 다르다.

## 무엇을 약속하지 않는가

텍스트 방식의 배치 복원은 **원리상 추정**이다. 글자 좌표에서 줄과 칸을 되짚는
것이라 다단·병합 표·회전된 글자에서 순서가 어긋날 수 있다. 그래서

- 표 추정은 기본으로 켜지 않는다. 사람이 켠다.
- 변환할 때마다 "읽는 순서·표를 확인하세요" 를 쪽마다 남긴다.
- 글자가 없는 쪽을 **조용히 이미지로 바꾸지 않는다.** 중단할지, 이미지로 넣을지,
  빼 버릴지 고르게 하고 기본값은 중단이다. 스캔 PDF 를 텍스트로 골랐다면
  그것은 사람이 잘못 고른 것이고, 말없이 다른 결과를 주는 편이 더 나쁘다.

## 되돌리는 값

작다. 두 단추와 `pdf-hwpx.ts` 의 `mode` 하나이고, 어느 쪽을 지워도 나머지는 선다.
다만 지우기 전에 어느 쪽이 안 쓰이는지 볼 방법이 없다 — 이 도구는 사용 기록을
남기지 않는다.
