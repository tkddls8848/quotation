# 결정 0008 — 완성된 코어의 전송 크기는 1.012 MiB 다. 관문 2 의 숫자를 고쳐 잡는다

- 날짜: 2026-08-27
- 상태: **적용됨**
- 고쳐 잡는 결정: [결정 0007](0007-phase0-gates-passed.md) 의 관문 2-a
- 근거가 된 실측: [`measurements/runtime.md`](../measurements/runtime.md)

## 무슨 일이 있었나

결정 0007 은 관문 2-a(전송 1 MiB 이하)를 **0.799 MiB** 로 통과시켰다. 그때
WASM 에 들어 있던 것은 zip·XML·xlsx 라이브러리와 Phase 1 의 순수 규칙뿐이고,
견적서를 만드는 코드(Phase 4, `writer/`)는 아직 없었다.

이제 코어가 완성되어 다시 쟀다.

| | 결정 0007 (관문 측정용) | 지금 (완성된 코어) |
|---|---:|---:|
| 전송 자산 (gzip) | 0.799 MiB | **1.012 MiB** |
| 기동 | 4.2 ms | 5.1 ms |
| 변환 1건 | 78 ms (부분 작업) | 188 ms (실제 견적서) |

**기준을 1.2% 넘겼다.** 줄여 보려고 한 것들은 이만큼도 못 줄였다.

- `wasm-opt` 를 `--converge --strip-debug --strip-producers` 로 더 돌림: 0.4 KB.
- `umya-spreadsheet` 의 기능 플래그로 덜어 내기: **불가능하다.** 그 크레이트는
  기능 플래그가 없고 aes·sha2·이미지 처리까지 언제나 함께 온다.
- `panic = "abort"`: 워크스페이스 전체에 걸 수 없다 (PyO3 확장이 패닉을 파이썬
  예외로 바꿔야 한다). wasm32 에만 걸어도 눈에 띄는 차이가 없었다.

## 결론

**계속한다.** 관문 2-a 의 숫자를 **1.1 MiB** 로 고쳐 잡는다.

기준을 옮기는 것이 편의 때문이 아님을 적어 둔다. 이 관문이 물으려던 것은
"브라우저 자산 교체가 값어치를 하는가"였고, 답은 실측으로 이렇다.

| | 지금 (Pyodide) | Rust→WASM | 배수 |
|---|---:|---:|---:|
| 전송 자산 | 14.4 MiB | 1.012 MiB | **14배** |
| 기동 | 약 2,500 ms | 5.1 ms | 약 500배 |
| 변환 1건 | 약 300 ms | 188 ms | 1.6배 |

1 MiB 라는 숫자에는 근거가 없었다. 착수안 §1 이 적은 추정치(0.3~0.8 MiB)에
여유를 붙인 값이다. 그 추정이 틀렸다는 것이 이번 실측의 내용이고, 틀린 추정에
맞추려고 다시 쓰기(자체 OOXML 생성기)를 벌이는 것은 12 KB 값을 하지 않는다.

## 그럼 언제 멈추는가

새 기준은 **1.1 MiB** 이고, 다음 중 하나면 멈춘다.

- 전송 자산이 1.1 MiB 를 넘는다. 지금 여유는 90 KB 다.
- 브라우저 기동이 200 ms 를 넘는다. 지금은 5 ms 다.
- 변환 1건이 지금(Pyodide 약 300 ms)보다 느려진다.

세 번째가 중요하다. 이 전환이 사려던 것은 **첫 방문의 14.4 MiB 와 2.5 초**
이지 변환 속도가 아니었다. 변환이 지금보다 느려지면 사용자가 체감하는 것이
줄지 않으므로, 그때는 얻는 것이 없다.

## 남은 사실 하나

`umya-spreadsheet` 를 쓰는 한 자산의 절반쯤은 우리가 쓰지 않는 코드다
(aes·sha2·이미지). 직접 OOXML 을 적으면 훨씬 작아지겠지만, 그것은 Phase 4 를
다시 하는 일이고 동등성을 처음부터 다시 세워야 한다. 지금은 하지 않는다.
필요해지는 날(예: 전송 기준을 다시 절반으로 줄여야 하는 날)의 선택지로 남긴다.
