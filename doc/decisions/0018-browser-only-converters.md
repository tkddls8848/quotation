# 결정 0018 — HWP → PDF 를 내리고 변환기를 브라우저 안으로 되돌린다

- 날짜: 2026-09-16
- 상태: **적용됨**
- 뒤집은 것: [결정 0016](0016-a-server-only-for-hwp-to-pdf.md)
- 관련 결정: [결정 0002](0002-convert-in-browser.md),
  [결정 0010](0010-retire-the-server-conversion-path.md),
  [결정 0012](0012-one-folder-per-feature.md),
  [결정 0015](0015-both-pdf-to-hwpx-modes.md)

## 결론

**HWP(5.0) → PDF 기능과 `converters/server/` 를 지운다.** 그 자리에 브라우저만으로
확실하게 되는 변환 넷을 넣는다.

| 새로 들인 것 | 어디에 | 새 의존성 |
|---|---|---|
| PDF → 이미지 (PNG·JPEG, 여러 장이면 ZIP) | PDF 편집기 안 | 없다 (pdfjs-dist) |
| 이미지 → PDF (PNG·JPEG·그 밖은 캔버스 경유) | 새 화면 | 없다 (pdf-lib) |
| 텍스트·Markdown → HWPX | 새 화면 | 없다 (`hwpx-writer.ts`) |
| 인코딩 변환 (CP949 ↔ UTF-8, BOM, 줄바꿈) | 새 화면 | 없다 (`TextDecoder`) |
| ZIP 묶기·풀기 | 새 화면 | 없다 (fflate·`zip.ts`) |

도구 전체가 다시 한 문장으로 설명된다 — **고른 파일은 이 컴퓨터를 벗어나지 않는다.**

## 왜 내리는가

결정 0016 은 공개하기 전에 답이 있어야 할 것 셋을 스스로 걸어 두었다.
**셋 다 답이 없다.**

| 0016 이 건 조건 | 지금 |
|---|---|
| 한글이 내보낸 기준 PDF 와의 배치 비교 | 재지 못했다. 컨테이너에 함초롬체가 없어 Noto CJK 로 대체되고, 그 글꼴의 웹·컨테이너 재배포 권리가 불분명하다 |
| 실제 업무 문서와 동시 작업 부하 | 재지 못했다 |
| 운영 환경 (TLS·접근키·비용·글꼴 조건·GPLv3 배포 형태) | 정하지 못했다 |

그 위에 값이 더 든다. 이 앱은 Cloudflare 무료 계정의 **정적 자산 배포**다
(`main` 없음 — 결정 0002). HWP → PDF 만 830MB 짜리 LibreOffice + H2Orestart
컨테이너를 어딘가에서 따로 돌려야 하고, 그것은 배포 경로가 둘이 된다는 뜻이며
결정 0017 이 방금 하나로 줄인 것을 되돌린다. 무료 계정 Worker 의 요청당 CPU
10 ms 로는 어떤 변환도 성립하지 않으므로 Cloudflare 쪽으로 옮길 수도 없다.

결정 0016 이 치른 값도 컸다. "고른 파일은 브라우저 밖으로 나가지 않는다" 가
도구 전체의 성질에서 기능별 성질로 내려앉았고, 전송 동의·보관 기한·작업 토큰이
화면과 서버 양쪽에 붙었다. **쓰지 못하는 기능 하나 때문에 도구 전체의 약속이
약해져 있었다.**

## 무엇을 잃는가

**한글이 없는 PC 에서 .hwp 를 여는 길이 없다.** 이것이 이 결정의 대가이고,
숨기지 않는다. 화면은 `.hwp` 를 받으면 그 사실과 함께 데스크톱 경로를 안내한다.

한글이 깔린 Windows 에서는 `converters/desktop/hwp-to-hwpx.ps1` 이 그대로 있다.
한글이 제 형식을 직접 저장하므로 충실도는 그쪽이 가장 높다 — 0016 의 표에서도
그랬다. 잃은 것은 **한글이 없는 사람을 위한 차선책**이지 최선책이 아니다.

검증 기록은 지우지 않는다. 공개 문서 36건으로 잰 30/36 과 "그림·글상자 캡션이
빠진다" 는 [VALIDATION.md](../../converters/VALIDATION.md) 에 남긴다 — 이 길을
다시 열 사람이 같은 것을 두 번 재지 않도록.

## 무엇을 고른 기준

브라우저만으로 되는 변환은 많다. 셋으로 걸렀다.

1. **브라우저 JS/WASM 으로 확실하게 되는가.** 근사로만 되는 것은 넣지 않았다.
2. **내려받는 코드가 늘어나는가.** 넷 다 새 의존성이 0이다 — 이미 있는
   pdf-lib·pdfjs-dist·fflate 와 브라우저 내장 API 로 끝난다.
3. **못 하는 것을 화면에 적을 수 있는가.**

그래서 **DOCX·PPTX → PDF 는 넣지 않았다.** 수요는 가장 크지만 레이아웃 엔진이
필요하고, HTML 을 거치면 배치가 어긋난다. "충실도를 보장하지 못하는 변환은
내놓지 않는다" 는 이 도구의 규칙이 그대로 걸린다. XLSX·DOCX **읽기**(→ Markdown·
CSV)는 규칙에 걸리지 않으므로 다음 후보로 남겨 둔다 — 다만 그때는 새 의존성이
붙고, `quotation/` 의 Pyodide·openpyxl 을 부르는 것은 결정 0012 가 막으므로
따로 정해야 한다.

## 결정 0010 과의 관계

0010 은 **같은 변환을 두 곳에서 하던 두 벌 구현**을 지웠다. 0016 은 그것이
자기에게는 걸리지 않는다고 했고, 그 말은 맞았다 — 겹치는 구현이 없었다.
0018 이 0016 을 뒤집는 이유는 두 벌이어서가 아니라 **공개할 수 없어서**다.

## 무엇을 확인했는가

`converters/web/scripts/check-converters.mjs` 가 실제 Chromium 으로 공개 화면을
조작해 넷을 모두 본다 — PDF → 이미지(ZIP·낱장, PNG·JPEG 서명까지), 이미지 →
PDF(원본 크기·A4), 텍스트 → HWPX(표·제목·BinData 없음), 인코딩(CP949 판별·UTF-8
BOM 출력·담을 수 없는 글자에서 멈춤), ZIP(묶기·풀기). 단위 테스트 88건이 함께 돈다.

이 작업이 결함 하나를 잡았다. `zip.ts` 는 항목 이름을 늘 UTF-8 로 읽고 있었는데,
윈도우 탐색기가 만든 ZIP 은 한글 이름을 CP949 로 적으면서 그렇다고 표시하지
않는다. 내용은 멀쩡한 채 **이름만 깨지는** 갈래라 조용히 틀리던 자리다.
general purpose flag 의 bit 11 을 보고 없으면 UTF-8 로 엄격하게 읽어 본 뒤
어긋날 때만 CP949 로 보도록 고쳤고, 테스트로 못박았다.
