# 결정 0007 — Phase 0 관문을 모두 통과했다. 이식을 계속한다

- 날짜: 2026-08-27
- 상태: **적용됨**
- 근거가 된 실측: [`measurements/runtime.md`](../measurements/runtime.md)
- 관련: [착수안](../plan/rust-wasm-core-plan.md) §5, [일정](../plan/rust-wasm-core-schedule.md) §3

## 결론

관문 셋이 모두 통과했으므로 Phase 2 이후를 진행한다.

| 관문 | 기준 | 실측 | 판정 |
|---|---|---:|---|
| 1. 템플릿 도형·내용 보존 | `xlsx_parity` 기준 동등 | 셀 0건 차이, drawing 바이트 동일 | 통과 |
| 2-a. 전송 크기 | 1 MiB 이하 | 0.799 MiB (gzip) | 통과 |
| 2-b. 기동 | 200 ms 이하 | 4.2 ms | 통과 |
| 3. PyO3 확장이 배포 경로에 | 단일 EXE 에서 동작 | PyInstaller `--onefile` 에서 7/7 일치 | 통과 |

## 정정 — 변환 1건은 5~15 ms 가 아니다

착수안 §1 은 변환 1건을 5~15 ms 로 추정했다. **실측은 78 ms 다.**

원인은 코드 생성 품질이 아니다. 시간의 대부분은 템플릿 zip 을 열어 스타일과
시트를 파싱하고, 채운 뒤 다시 압축해 내보내는 데 들어간다. 이 일은 파이썬이든
Rust 든 같은 양이고, openpyxl 대신 `umya-spreadsheet` 를 써도 사라지지 않는다.

그래도 계획을 접지 않는다. 이 계획이 사려던 것은 **첫 방문자가 14.4 MiB 를
받고 2.5 초를 기다리는 문제**였고 그쪽은 예상대로다.

| | 지금 | Rust→WASM | 배수 |
|---|---:|---:|---:|
| 전송 자산 | 14.4 MiB | 0.799 MiB | 18배 |
| 기동 | 약 2,500 ms | 4.2 ms | 약 600배 |
| 변환 1건 | 약 300 ms | 78 ms | 4배 |

착수안 §3 의 "서버 변환(B안)이 무료 계정에서 성립한다"는 전망은 **성립하지
않는다.** Workers Free 의 요청당 CPU 한도는 10 ms 인데 78 ms 는 그 8배다.
B 안은 원래도 범위 밖이었고, 이 실측으로 근거가 하나 더 사라졌다. 브라우저
WASM(A안)만 남는다.

## 크기와 속도를 맞바꾼 자리

`[profile.release] opt-level` 을 `3` 으로 두면 변환이 54 ms 로 줄지만 전송이
1.001 MiB 가 되어 관문 2 기준을 넘는다. 그래서 `"z"` 를 쓴다. 기준을 넘겨
가며 24 ms 를 사지 않는다.

`panic = "abort"` 는 쓰지 않는다. 크기 이득이 없었고(0.799 MiB 로 동일),
PyO3 확장은 패닉을 되잡아 파이썬 예외로 바꿔야 하므로 워크스페이스 전체에
걸 수 없다.

## 이 판정이 아직 답하지 않은 것

- 브라우저 실측이 아니다. node 23 에서 쟀다. 실제 Chromium 수치는 Phase 5 에서
  `web/tests/test_browser_e2e.py` 경로로 다시 잰다.
- 78 ms 는 견적서를 만드는 값이 아니라 zip·XML·셀·zip 을 한 번씩 지나가는
  값이다. Phase 4 가 끝나면 같은 자리에서 다시 잰다.
