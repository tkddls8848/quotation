# 결정 0009 — 브라우저 동일성은 ZIP 바이트가 아니라 내용으로 판정한다

- 날짜: 2026-08-28
- 상태: **적용됨**
- 잇는 결정: [결정 0005](0005-accept-meaningful-xlsx-parity.md)
- 바뀐 검사: `web/tests/test_browser_parity.py`, `web/tests/test_browser_e2e.py`

## 무슨 일이 있었나

브라우저 엔진을 Pyodide 에서 Rust→WASM 으로 바꿨다. 그러자 두 검사가 붉어졌다.

- `test_browser_xlsx_is_byte_identical` — `.xlsx(zip)` 의 모든 부품을 바이트로
  비교한다.
- `test_browser_xlsx_matches_cell_by_cell` — 골든 비교기(`tools/compare.py`)로
  본다. 이 비교기는 색을 **적는 방식** 까지 구별한다.

붉어진 까닭은 견적서 내용이 아니라 **OOXML 을 적는 라이브러리가 달라서** 다.

| | 브라우저 (Rust→WASM) | CPython (openpyxl) |
|---|---|---|
| 색 표기 | 팔레트 색인 `27` | ARGB `FFCCFFFF` (같은 색) |
| 문자열 | `sharedStrings.xml` 로 모음 | 셀 안에 그대로 |
| 프린터 설정 | 템플릿 것을 그대로 들고 감 | 버림 |
| 부품 순서·압축 | zip 라이브러리마다 다름 | |

지금까지 이 검사가 성립했던 것은 **양쪽 다 openpyxl 이었기 때문** 이다. 같은
라이브러리 두 벌을 견주고 있었으므로 바이트가 같았다.

## 결론

브라우저 동일성 검사도 [결정 0005](0005-accept-meaningful-xlsx-parity.md)의
기준을 쓴다. **Excel 이 읽는 내용**과 **첫 페이지 도형**이다.

바뀐 뒤 검사가 지키는 것:

1. 값·수식·표시 형식·글꼴·채우기·테두리·정렬·병합·인쇄 영역·행 높이·시트
   차례를 셀 단위로 비교한다. 색은 팔레트 색인과 ARGB 를 같은 색으로 본다.
2. 서버 산출물에 있는 **부품이 하나라도 빠지면 실패** 한다. 더 실리는 것은
   진단으로 찍고 막지 않는다 (프린터 설정·공유 문자열이 그렇다).
3. 첫 페이지의 로고·머리글 도형은 **템플릿 원본과 바이트까지 같아야** 한다.
4. 상태 코드·다운로드 이름·`X-Template-Version`·구조화 로그 항목은 그대로
   서버와 같아야 한다. 거절도 같은 코드·같은 문구여야 한다.
5. 실제 Chromium 에서 받은 파일도 같은 기준으로 대조한다 (E2E).

## 무엇을 잃는가

바이트 비교는 "아무것도 달라지지 않았다"를 한 줄로 보증했다. 그 보증은
사라진다. 대신 위 다섯 가지가 남고, 그중 1·3 은 사람이 눈으로 볼 수 있는
것 전부를 덮는다.

느슨해진 자리를 정직하게 적어 둔다. **두 라이브러리가 같은 색을 서로 다른
표기로 적어도 통과한다.** 화면에 나오는 색은 같지만, 예컨대 팔레트가 다른
템플릿을 쓰게 되면 표기 차이가 색 차이가 될 수 있다. 그런 날이 오면 이
결정을 다시 본다.

## 남겨 둔 것

`web/tests/xlsx_parity.py` 는 지우지 않는다. 같은 라이브러리끼리 견주는
자리(예: 파이썬 구현끼리의 회귀)에서는 여전히 가장 촘촘한 판정기다.
