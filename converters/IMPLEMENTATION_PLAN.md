# PDF ↔ 한글 문서 변환 구현 계획

작성일: 2026-09-14  
상태: 계획 단계. 서버 도입 및 운영 환경은 미정.

## 목표와 구현 순서

현재 문서 변환기의 PDF 편집 기능과 HWPX 읽기를 기반으로 다음 순서로 확장한다.

| 단계 | 기능 | 처리 위치 | 목표 |
|---|---|---|---|
| 1 | PDF → HWPX 이미지 방식 | 브라우저 | 쪽의 모양과 순서 유지 |
| 2 | HWP(5.0) → PDF | 품질 검증 후 별도 변환 서버 | 검증된 문서 유형부터 지원 |
| 3 | PDF → 편집 가능한 HWPX | 브라우저 우선 | 글·문단·단순 표 재구성 |

이미지 방식도 해상도에 따른 차이가 생기므로 시각적 일치를 100% 보장하지 않는다.
LibreOffice 변환도 원본과의 일치를 검증해야 하며 유일한 변환 경로로 단정하지 않는다.
기존 화면과 README의 관련 표현은 기능 구현 시 함께 수정한다.

## 1단계: PDF → HWPX 이미지 방식

### 처리 흐름

PDF 입력 → 쪽 선택·순서·회전 적용 → PDF.js로 쪽별 그림 생성 → HWPX 쪽에 배치 → ZIP 패키징 → 다운로드.

PDF.js는 브라우저 Canvas 렌더링을 지원한다. 기존 PDF 편집기의 쪽 선택·순서·회전 결과를 연결한다.

### 구현 범위

- HWPX 생성 모듈과 ZIP 쓰기 기능을 추가한다. 현재 HWPX 읽기 코드는 유지하고 생성기를 별도로 둔다.
- 그림 한 장이 들어간 최소 HWPX부터 생성하고, 한글에서 정상적으로 열리는지 검증한다.
- 한컴 공개 OWPML 모델을 참고해 문서 구조, 그림 참조, 패키지 구성을 확인한다.
- 원본 쪽 크기와 가로·세로 방향을 반영한다. 서로 다른 쪽 크기가 섞인 PDF도 검증한다.
- 품질 옵션은 150·200·300 DPI로 시험하고 기본값은 품질·파일 크기·메모리 측정 후 정한다.
- 진행률과 취소 기능을 제공한다. 쪽별로 처리하고 사용이 끝난 렌더링 자원을 회수한다.
- 이미지 변환용 입력 크기·쪽 수·총 픽셀 수·출력 크기 한도를 측정해 정한다. 기존 PDF 편집기의 1,000쪽 한도를 그대로 적용하지 않는다.
- 암호화·손상된 입력, 메모리 한도 초과, 생성 실패를 안내하고 불완전한 결과를 성공으로 표시하지 않는다.

### 사용자 안내

기능 이름은 `PDF → HWPX (이미지)`로 구분한다. 글자와 표가 그림으로 저장되어 직접 편집할 수 없음을 표시한다.
파일은 브라우저 안에서 처리한다.

### 완료 기준

- 한글에서 복구 경고 없이 열린다.
- 선택한 쪽 수·순서·크기·회전이 출력과 일치한다.
- 그림 잘림과 불필요한 빈 쪽이 없다.
- 원본과 출력의 시각 비교에서 글자·표·그림 누락이 없다.
- 여러 쪽 변환, 취소, 오류 처리, 다운로드를 실제 브라우저에서 확인한다.

## 2단계: HWP(5.0) → PDF

### 먼저 수행할 품질 검증

LibreOffice + H2Orestart로 대표 문서를 변환한다. 공식 headless PDF 변환 경로를 이용하되 모든 문서의 배치 일치를 전제하지 않는다.

- 병합 표, 머리말·꼬리말, 그림, 수식, 다단, 서로 다른 글꼴을 포함한 검증 문서를 준비한다.
- 한글에서 내보낸 기준 PDF와 비교한다.
- 쪽 수·줄바꿈·표 잘림·글자 누락·그림 위치를 점검한다.
- 글꼴 설치 및 사용 조건을 확인하고, 대체 글꼴이 만드는 차이를 기록한다.
- 지원 가능한 문서 유형과 알려진 실패 유형을 정리한 뒤 공개 여부를 판단한다.

### 품질 검증 통과 후 서버 구성

브라우저 업로드 → 작업 접수 → 격리된 변환 작업 → 상태 조회 → PDF 다운로드 → 기한 만료 후 파일 삭제.

- 기존 웹 화면과 별도로 변환용 컨테이너 서버를 구성한다.
- 작업 접수·상태 조회·다운로드 인터페이스를 제공한다.
- 작업마다 임시 폴더와 LibreOffice 프로필을 분리한다.
- 시간·메모리·파일 크기·동시 작업 수를 제한하고, 시간 초과 시 관련 프로세스를 종료한다.
- 변환 프로세스의 매크로 실행과 외부 네트워크 접근을 차단한다.
- 작업별 접근 권한을 검증하여 다른 사용자의 원본이나 결과를 조회할 수 없도록 한다.
- 원본·결과·변환 로그에 삭제 기한을 적용한다. 로그에도 문서 내용 일부가 남을 수 있으므로 함께 관리한다.
- 실패, 취소, 서버 재시작 후에도 임시 파일이 정리되는지 확인한다.

### 화면 변경

- 업로드 전에 서버 전송 사실을 표시한다.
- 기존의 모든 파일이 브라우저 안에서만 처리된다는 안내를 기능별 안내로 수정한다.
- 대기·변환 중·완료·실패·만료 상태와 결과 다운로드를 제공한다.
- 알려진 글꼴 및 배치 차이를 안내한다.

### 공개 판단 및 대안

품질이 기준에 못 미치면 공개를 보류한다. 기존 Windows 한글 자동화 경로를 활용한 로컬 PDF 변환 대안을 검토한다.
서버 운영 환경·비용·글꼴 사용 조건·배포 방식에 따른 라이선스 검토는 품질 검증 후 구체화한다.
이 계획만으로 유료 자원 생성이나 서버 배포를 진행하지 않는다.

### 완료 기준

- 검증 문서군에서 내용 누락과 심각한 표·쪽 배치 오류가 없는 지원 범위를 확정한다.
- 실패 문서를 정상 완료로 표시하지 않는다.
- 동시 작업이 서로의 파일이나 변환 프로필에 영향을 주지 않는다.
- 업로드부터 다운로드까지의 흐름과 시간 초과·삭제 기한·접근 권한을 검증한다.

## 3단계: PDF → 편집 가능한 HWPX

이미지 방식과 별도 옵션으로 제공한다. 레이아웃을 재구성하는 기능이며 원본 배치의 완전한 복원을 약속하지 않는다.

### 구현 범위

- 첫 버전은 텍스트가 포함된 PDF의 글·문단·단순 표만 지원한다.
- 글자 좌표에서 읽는 순서와 문단을 추정하고 HWPX 요소로 생성한다.
- 1단계에서 검증한 HWPX 패키지 생성부를 같은 기능 폴더 안에서 재사용한다.
- 복잡한 병합 표·다단·수식은 지원 범위를 명시하고 확인이 필요한 쪽을 표시한다.
- 스캔 PDF의 OCR은 후속 단계로 둔다.
- 인식 실패를 이미지로 조용히 대체하지 않는다. 해당 쪽의 이미지 처리 또는 제외 여부를 사용자가 선택하게 한다.

### 완료 기준

- 지원 문서군에서 글자 누락·중복과 읽는 순서 오류를 점검한다.
- 한글에서 문단과 단순 표를 실제로 수정하고 다시 저장할 수 있다.
- 재구성이 불확실한 쪽을 사용자에게 표시한다.
- 스캔 PDF 등 지원하지 않는 입력을 명확하게 안내한다.

## 코드 배치와 검증 원칙

- 기능 코드와 테스트는 `converters/` 안에 둔다. 다른 기능인 `quotation/`, `fire/`를 호출하지 않는다.
- 셸은 기존 `mountConverters` 진입점을 통해 화면을 연결한다.
- PDF 렌더러와 변환 의존성은 해당 기능을 사용할 때 불러오도록 구성한다.
- 기존 HWPX 읽기와 PDF 편집 테스트, 기능 경계 검사, 타입 검사, 빌드를 유지한다.
- HWPX 패키지 구조 검사만으로 완료 처리하지 않고 실제 한글 열기 검증을 수행한다.
- HWP → PDF는 생성 성공 여부뿐 아니라 기준 PDF와의 내용·배치를 비교한다.

## 첫 구현 단위와 결정 시점

첫 구현 단위는 `PDF 한 쪽 → 그림 한 장을 포함한 HWPX → 한글에서 열기 검증`이다.
이 검증이 통과하면 여러 쪽 처리와 기존 PDF 편집기 연결로 확장한다.

| 결정 항목 | 결정 시점 |
|---|---|
| 이미지 해상도 기본값과 변환 한도 | 1단계 품질·메모리 측정 후 |
| 검증 대상 한글 버전과 문서군 | 최소 HWPX 호환성 검증 시작 시 |
| HWP → PDF 지원 문서 범위 | LibreOffice + H2Orestart 비교 검증 후 |
| 서버 환경·비용·보관 기한·접근 정책 | 서버 연동 구현 전 |
| OCR 및 복잡한 표 재구성 | 3단계 기본 기능 검증 후 |
